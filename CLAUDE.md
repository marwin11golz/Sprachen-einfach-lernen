# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm install     # install dependencies
npm run dev     # start Vite dev server (http://localhost:5173)
npm run build   # production build to dist/
npm run preview # preview the production build locally
```

There is no lint, format, or test tooling in this repo — no ESLint/Prettier config, no test runner, no test files. The verification loop is therefore: `npm run build` (catches syntax/import errors only) **plus** actually exercising the change in a browser — either the `run` skill, or `npm run preview` driven with Playwright. For anything touching scheduling, answer checking, or speech, drive the real UI and assert on the outcome; a green build says almost nothing about correctness here.

## Architecture

Single-page Vite + React app, "Sprachen lernen" — a flashcard vocabulary trainer with spaced repetition. Deliberately no router and no state-management library. Data is local-first (`localStorage`); Supabase cloud sync is an optional layer that the app runs fine without.

### Module layout

The data layer is deliberately separated from the UI so that database work and design work don't collide.

**Domain / data**

- **`src/lib/fsrs.js`** — the FSRS-6 scheduling core (stability/difficulty/retrievability/interval formulas, standard weights) plus the fixed target retention (`RETENTION`). Pure functions, no imports.
- **`src/lib/srs.js`** — domain logic built on `fsrs.js`: `rate(card, rating)`, the card factories `newVocabCard`/`newGapCard`, `levenshtein()`, `splitAnswer()`/`cardSides()`, gap-sentence helpers (`parseGapLine`/`maskSentence`/`revealSentence`), `deckKeyOf`/`deckLabelOf`, and the `LANGUAGES` table. **Single source of truth for the card shape and the scheduling algorithm.**
- **`src/lib/storage.js`** — `localStorage` read/write plus schema migration. Persisted shape (v2): `{ schemaVersion, cards, activityLocal, activityRemote, flipped, newCardsPerDay, retention, prefsUpdatedAt, lastUserId, lastSyncAt }` under the key `lucy-lernt-sprachen-vocab-data`. That key still carries the app's old name on purpose — renaming it would orphan every existing user's data.
- **`src/lib/merge.js`** — `mergeCards()` (per-card last-write-wins on `updatedAt`, ties resolved by `pickWinner()`), `combinedActivity()`, `purgeOldTombstones()`. Used by both the import path and cloud sync, so there is exactly one merge rule.

**Cloud sync (optional)**

- **`src/lib/supabase.js`** — client, or `null` when `VITE_SUPABASE_URL`/`VITE_SUPABASE_ANON_KEY` are absent. `cloudConfigured` is the flag every caller checks; without it the app stays purely local instead of crashing.
- **`src/lib/sync.js`** — `syncNow()`/`syncOnce()`: fetch everything → merge → derive the push set from the merge result. Takes the client as an argument rather than importing it, so it is testable without a network. Always fetches the full card set (a personal deck is tiny, and it removes the whole "which change did I miss" failure class). `syncNow()` de-dupes concurrent calls via an in-flight promise.
- **`src/hooks/useAuth.js`**, **`src/hooks/useCloudSync.js`** — auth session, and *when* to sync (on sign-in, debounced after local edits, on reconnect/foreground). Sync is paused while `view === 'study'` so a remote state can't overwrite a card being rated.

**UI**

- **`src/lib/theme.js`** — the design system: `SPACE`/`RADIUS`/`FONT`/`NAVBAR_H` scales, `THEMES` (light/dark palettes), and the style helpers `btnPrimary`/`btnSecondary`/`btnOutline`/`btnGhost` (each with `sm`/`md`/`lg` sizes), `pill`, `ratingBtn`, `surface`, `surfaceSoft`, `divider`, plus the `typo*` family. Inline styles throughout; no CSS framework. **All hardcoded spacing/radius/font values have been removed.** Reach for these tokens rather than fresh magic numbers — spacing: `{ xs:4, sm:8, md:12, lg:16, xl:24, xxl:32, xxxl:48 }`, radius: `{ sm:6, md:8, lg:12, pill:999 }`, font: `{ xs:11, sm:12, base:13, md:14, lg:16, xl:18, xxl:22, hero:32 }`. This discipline ensures visual consistency across all changes.
- **`src/hooks/useVocabStore.js`** — owns `cards`, activity, `flipped`, `newCardsPerDay`, persistence. Exposes **only intent-based actions** (`addCards`, `rateCard`, `deleteCard`, `deleteCards`, `importData`), never a raw `setCards` — that is what guarantees every mutation stamps `updatedAt`.
- **`src/App.jsx`** — all UI. Views are toggled by a single `view` state: `dashboard` / `add` / `browse` / `settings` render as conditional blocks inside the main return, but **`study` returns early as its own full-screen layer** (before the header and bottom nav) so the learning session has no surrounding chrome. Two top-level `return`s, not one.
- **`src/ui/AuthScreen.jsx`**, **`src/ui/SyncBadge.jsx`**, **`src/ui/SessionDone.jsx`**, **`src/ui/StreakCelebration.jsx`** — the only extracted components. `useHochzaehlen`/`magKeineBewegung` live in `src/lib/motion.js`, shared by the two animated screens rather than duplicated.

### Sync-critical invariants

- **Every card carries `updatedAt`** (full ISO timestamp) and **`deleted`** (tombstone flag). Deleting sets `deleted: true` rather than removing the card — otherwise the other device resurrects it on the next merge.
- **Migration derives `updatedAt` from `lastReviewed`/`createdAt`, never from `Date.now()`.** Both devices hold copies of the same legacy cards, so stamping "now" would let whichever device opens the app second win every card and silently overwrite the other's review progress. Deterministic derivation produces a tie instead, which `pickWinner()` resolves in favour of higher `totalReviews` — a tie must never cost progress.
- **Activity is split into `activityLocal` (this device) and `activityRemote` (sum of others)**; only `activityLocal` is ever pushed. Pushing the combined value would make the counts inflate on every sync.
- **`cardToRow()` sends the client's `updatedAt`, not `now()`** — otherwise every uploaded card would look new on the next pull and the devices would ping-pong forever. Timestamps from Postgres go through `normalizeStamp()` because `"…+00:00"` and `"…Z"` are the same moment but compare differently as strings.
- `useVocabStore` keeps a `revision` counter bumped only by real user edits — applying a remote state must not bump it, or every pull would trigger a push.
- **Preferences sync carries only `flipped`.** `newCardsPerDay` is deliberately local-only: it's a pacing preference, not progress, and keeping it out means zero changes to `sync.js`. `retention` is no longer a preference at all — it is a fixed constant, and the `retention` value in `localStorage` is only the migration marker described below.

### Domain conventions worth knowing

- **Sort fields carry their own default direction** (`SORTIERFELDER` in `App.jsx`). Due date opens ascending (what's next comes first), error rate descending (the worst first) — a single shared default had the error-rate column upside down, listing the cards you least need to see. Cards never reviewed get `-1` rather than a made-up `0`, so they land at the end instead of among the error-free ones. Each desktop column header sorts by what that column *shows*; `Zuletzt angelegt` and `Fehlerquote` have no column and are reachable only through the dropdown, which is therefore visible at every width.

- **The Fehlerkartei (error deck) admits on `wrong > 0` but releases on a recovery streak, not on `wrong` itself.** `wrong` never decrements by design (see `repetitions` below — progress counters don't shrink), so membership can't hang off `wrong > 0` alone: the deck would only ever grow, no matter how many times a card was answered correctly since. `isDifficult()` in `App.jsx` also requires `erholungsStreak(c) < FEHLERKARTEI_ERHOLT` (3), reading the card's `recoveryStreak`. A card leaves after three **confident** recoveries in a row and returns the moment it lapses *or* is rated hard again.
  - **`recoveryStreak` counts only `good`/`easy`; `hard` resets it to 0, exactly like `again`.** Hard is the rating that means "this one still isn't sitting" — a card dragged out of memory three times with effort is precisely the one worth keeping in the deck, and releasing it there would defeat the deck's purpose.
  - **It has to be its own field, even though `earlyStep` counts something nearly identical.** `earlyStep` picks the due date on the fixed ladder and therefore *must* advance on hard (`hard` has its own row in `EARLY_STEPS`), or a card rated hard would never move off its rung. The two counters diverge on exactly one rating, and that rating is the whole point — hence two.
  - Cards predating `recoveryStreak` fall back to `earlyStep` (and, through it, to `totalReviews`) in `erholungsStreak()`, which is the counter membership hung off before, so introducing the field changed no existing card's membership. No migration was needed — same reason as `earlyStep`: `cardToRow()` packs unknown fields into `data` and `migrateCard()` spreads the card whole.
  - **Studying from the Fehlerkartei rates through `drillCard()`/`drill()`, not `rateCard()`/`rate()`.** `submitRating()` in `App.jsx` branches on `deckFilter === DECK_FEHLER`. `drill()` in `srs.js` touches only `recoveryStreak`; `interval`/`dueDate`/`stability`/`difficulty`/`earlyStep`/`totalReviews`/`repetitions`/`correct`/`wrong` and the daily activity log are all left exactly as they were. The Fehlerkartei is meant as a free-standing drill, not a second inflow into the same schedule — before this split, two "Gut" ratings in one sitting advanced `earlyStep` twice and pushed the *real* due date out by a normal review's worth of days, so a card you'd only half-recalled under quick drilling could vanish from sight for a week. Because `interval` never changes in drill mode, the same-session requeue rule (§ "Zurueck in die Warteschlange") reads the *rating* instead: `hard` resets `recoveryStreak` exactly like `again` does, so both bring the card right back in the drill queue; `good`/`easy` do not. `sessionRatings` (the in-progress "Karten gelernt"/Trefferquote shown by `SessionDone`) still updates during drilling — that counter is ephemeral, per-session UI feedback, not persisted card state, so showing it doesn't reopen the door drilling closed.
- **`repetitions` equals `totalReviews + 1`** and is never reset by an "again" rating (that was an SM-2 concept). Resetting it would make a forgotten, long-learned card count as "new" again in the dashboard and in the daily limit.
- **Legacy SM-2 cards are seeded lazily.** `seedFromLegacy()` in `srs.js` derives `stability`/`difficulty` from the old `interval`/`ease` on the card's first rating after the upgrade — due dates are untouched, so no card jumps. `rescheduleCard()` is the one exception: it seeds immediately, because it rewrites `interval`, and `seedFromLegacy()` reads exactly that field as its stability estimate.
- **The first seven reviews run on a fixed ladder, not on FSRS's own intervals.** `EARLY_STEPS` in `fsrs.js` holds one row per rating — `hard: [0,1,2,4,7,12,20]`, `good: [1,3,7,16,35,70,140]`, `easy: [3,7,18,40,80,160,320]` — and `rate()` overrides *only the due date* with it. Stability and difficulty keep being written from the **actually elapsed** days throughout, so the model stays coherent and FSRS takes over seamlessly at step 8. The reason: the reference weights are fitted on large Anki collections where "Einfach" is used sparingly; unchecked, a card rated Einfach twice already sits 52 days out, then 167. Three consequences worth knowing:
  - **`again` has no row on purpose.** A forgotten card gets the interval FSRS computes from its own stability, and its `earlyStep` falls back to 0 — otherwise the next "Gut" after a lapse would hand out step 6's 70 days.
  - **`earlyStep` is a persisted card field.** It cannot be derived from `totalReviews`, because a lapse resets it. Cards predating the field fall back to `totalReviews`, so they join the ladder at a sensible rung. No migration was needed — `cardToRow()` packs unknown fields into `data`, and `migrateCard()` spreads the card whole.
  - **`hard` step 0 is an interval of `0`** — the "10 minutes" step. `dueDate` is a date, never a time, so the equivalent is: the card stays due today and `submitRating` in `App.jsx` puts it back into the running session (the same re-queue that `again` uses). Do not read this as "no interval".
- **After the ladder, `hard` is capped at `HARD_FAKTOR` (0.9) × the previous interval** (`hardInterval()` in `fsrs.js`, applied in `rate()`). `nextInterval(S)` knows only the stability, so once the ladder is done the rating drops out of the scheduling entirely — it survives only as the `W[15]` damping on stability *growth*. That was far too weak to be legible: a card recalled with effort after 140 days jumped to **222** days, i.e. further out than last time and barely a fifth below the 272 that `good` would have handed out. The cap only bites downward — where FSRS computes something smaller (a card with low stability), the smaller number still wins — and never falls below one day. The factor sits deliberately below Anki's `hard` (1.2 there): at 1.2 a card recalled with effort five times running would still climb 140 → 168 → 202 → 242 → 290, so "hard" would mean *slower growth* rather than *sooner again*. At 0.9 the same card walks back: 140 → 126 → 113. `good` and `easy` are untouched, so the reference sequence for eight `good` ratings is still `1 → 3 → 7 → 16 → 35 → 70 → 140 → 272`.
- **Target retention is fixed at `0.95`** (`RETENTION` in `fsrs.js`) — no knob, no setting, and `nextInterval(S)` takes no retention argument. The value sits deliberately above Anki's `0.9`, under which a card rated "Gut" runs 2 → 11 → 46 → 163 days and everything already learned disappears for months. It is fixed because it is the one quantity in the model that does *not* come from the learner's behaviour: stability, difficulty and retrievability are all computed from actual ratings, and a knob beside them invites tuning the schedule instead of letting the ratings speak. Since the fixed ladder above, it only governs what happens **after** step 7 anyway — `rescheduleCard()` returns cards still on the ladder untouched.
- **`storage.js` keeps a `retention` field, but only as a marker of which curve the deck is scheduled on.** `loadLocal()` derives `needsRetentionReset: parsed.retention !== RETENTION`; `useVocabStore` then runs `rescheduleCard()` over the deck once, and `saveLocal()` always writes `RETENTION` back, so the migration never runs twice. It catches two groups at once: users who predate target retention entirely, and users who had turned the old density knob down — the latter carry cards sitting 674 days out that the fixed `0.95` would otherwise never reach again. The rewrite deliberately does **not** stamp `updatedAt`: the calculation is deterministic, so every device reaches the same result on its own, and stamping could let the device opened first overwrite the other's unsynced ratings.
- **No interval number appears anywhere in the UI.** Scheduling is background work: the rating buttons carry no day counts, and the ladder's sequences live in comments in `fsrs.js`, not on screen. Someone who reads that a card returns in 272 days starts rating the number instead of their own recall. The card list's per-card `fällig <date>` is not an exception — a due date says when *this* card is next up, not what a rating hands out.
- **Elapsed time is counted in calendar days** (`daysBetween()`), never by rounding a clock difference. Rounding `Date.now()` against midnight of `lastReviewed` charged an extra day to everyone studying after midday, which inflated stability at every single review and pushed cards ever further out.
- **The daily new-card limit caps only new cards.** In `startStudy()`, the pool is split into reviews (`repetitions > 0`, never capped — that's the point of spaced repetition) and new cards (sorted oldest-`createdAt` first, capped by `newCardsPerDay` minus what was already introduced today). "Alle wiederholen" bypasses the cap entirely. The "introduced today" count is *derived* from the cards (`totalReviews === 1 && lastReviewed === today`), not stored — that keeps it correct across multiple sessions and a sync in between.
- **A `|` or a spaced dash splits answer from example sentence on *either* side of a vocab card** (`splitAnswer()`, applied to both sides by `cardSides()`). Only the part before the separator is typed and checked; the rest is context. The dash *must* be surrounded by spaces so `E-Mail` and `well-known` survive, and en/em dashes count because phone keyboards autocorrect `" - "` into `" – "`. **Each sentence belongs to its own language**: `casa | Vivo en una casa. = Haus | Ich wohne in einem Haus.` shows the Spanish sentence on the Spanish side and the German one on the German side, and they swap together with `flipped`. That is why a back-side sentence can no longer leak onto the front and give the answer away. Cards carrying only one sentence keep it on the translation side and work unchanged — no migration was needed, because the sentence never was its own field.
- **Language names in `LANGUAGES` are persisted card data** (`langA`/`langB`/`language`). Renaming an entry orphans existing cards' language; adding entries is safe. Each carries a BCP-47 `code` used for speech — without it the browser reads every word in the default voice, so English "future" comes out German.
- **The add view detects the language of a pasted block and sets the picker itself** (`src/lib/spracherkennung.js`, wired through the debounced effects next to `handleAddVocab` in `App.jsx`). Because the language is copied onto every card at creation time and there is no editing, a stale picker silently mislabels a whole batch and the only repair is deleting and re-pasting it — the single most expensive mistake the add view allows. Four things hold this together:
  - **It only needs to find the *foreign* language and which side it sits on.** Every entry in `VOCAB_PAIRS` has German on one side, so the other side follows without being detected — which matters because the German side is typically a bare noun ("Wettbewerbsvorteil") with no function words to score, while the foreign side carries the example sentence and therefore plenty of evidence.
  - **Silence beats a guess.** `erkenneSprache()` returns `null` unless the winner clears both an absolute score and a 1.5× margin over the runner-up; Spanish and Portuguese share half their function-word lists, and a confident wrong answer would be exactly the damage the feature exists to prevent. Non-Latin scripts short-circuit the word scoring, with kana tested before CJK because Japanese also writes in Chinese characters.
  - **The picker itself is the feedback** — it visibly changes to the detected pair, and nothing else announces it. An earlier version added a caption underneath ("Sprache erkannt – auf … gestellt"); it was removed on request, and the reasoning survives the removal: the safety property that matters is that a wrong guess is *visible before the cards are created*, and the changed picker already carries that. A second line saying the same thing was noise on a screen whose whole job is the textarea below it.
  - **A manual pick binds only while the textarea has text.** Choosing a pair with the box *empty* is pre-setting on spec — exactly the situation that goes wrong — so detection may still correct it; choosing one with the block visible is a deliberate disagreement and is left alone until the box empties. Tying it to emptiness instead of to the debounce is what keeps the behaviour from depending on whether 300 ms happened to elapse between picking and pasting.
  - `vokabelZeilen()` in `App.jsx` splits the pasted block for **both** the detector and card creation. One splitter on purpose: if the two disagreed about where a line divides, the detector would score a different text than the one that ends up on the card.

### Design aesthetic: Anki-style

The app's visual design targets a professional, utilitarian look (inspired by Anki) rather than decorative/playful. Changes prioritize clarity and efficiency: smaller radius, flatter shadows, tighter spacing, smaller font scale. This is enforced through the design token system — no hardcoding. When styling a new component, use `SPACE`/`RADIUS`/`FONT`/`THEMES` tokens exclusively. If a value doesn't fit the scales, it means the component needs rethinking, not a new magic number.

Two rules the color system rests on, both enforced by hand — nothing checks them at build time:

- **One filled green button per screen.** `btnPrimary` marks the single main action; every competing action uses `btnOutline` (or `btnGhost`). Two filled buttons side by side read as two main actions and the screen loses its center of gravity.
- **Green means "act now", not "this is a number".** `primary` carries the main action, the active state, progress and the key figures; `success`/`warning`/`error` are reserved for immediate feedback (rating buttons, toasts) and must not be borrowed as a second accent — `success` and `primary` are nearly the same green and reading two of them on one screen is what "leicht variierende Grüntöne" means. Categories are distinguished by the *shape* of their icon, never by a color of their own: that is why the Fehlerkartei's warning triangle is green like every other deck icon.

### UI gotchas

- **The study card tracks two separate states, and conflating them is the bug that was already there once.** `revealed` means "the answer is out" — a one-way switch per card that gates the rating buttons and, in write mode, keeps the input from coming back. `zeigtRueckseite` means "which side is face up" and toggles freely. When these were one flag, revealing a card destroyed the question for good: to look at the Spanish word again you had to rate the card and wait for it to come round. Tapping the card calls `dreheKarte()`, which reveals on the first tap and flips on every one after. The card stays untappable in write mode until `checkWrite()` runs, otherwise typing could be skipped.
- **"Richtung" and "Umdrehen" are different things and must not share a word.** The `flipped` button in the study toolbar reverses the whole deck's direction (Spanisch→Deutsch instead of the reverse) and persists across cards and sessions; flipping *the card* affects only the card in hand. `flipped` is the one preference that syncs to the cloud, which is exactly why it can't be the per-card gesture.
- **The session-complete screen is the app's one animated moment** (`ui/SessionDone.jsx`). Its choreography comes from a design canvas: check mark, title, three figures and the button stagger in via `animation-delay` on the `dc-*` classes in `globalCss`, and the numbers count up in `useHochzaehlen`. Two things it gets right and a rewrite must keep: the classes use `animation-fill-mode: backwards` so an element waits in its *from* state and — when the animation is switched off — simply sits finished, which is what makes `prefers-reduced-motion` a one-line override; the one exception is `.dc-glow`, which needs `both` because its end state (invisible) must survive, otherwise the ring reappears at full opacity the moment the animation ends. The palette is deliberately the app's tokens, not the canvas's own dark colours — the draft only had a dark version. Wording and structure, however, follow the draft exactly: "Session abgeschlossen", no explanatory subtitle (it would repeat the first figure verbatim), and the button reads "Zur Übersicht". `FONT.display` (44) exists for this screen's figures — the one place where the numbers are the content rather than an accent.
- **`StreakCelebration.jsx` only shows on the day the streak actually advances** (`streakNeu`, set in `startStudy()` from `reviewsToday === 0` — before this session's own rating logs today's activity and makes that check useless). It's a second screen *after* `SessionDone`, not a replacement: `SessionDone` is always the first thing shown when a session ends, and only its own button decides whether the next stop is the streak screen or the dashboard — this keeps the ordinary summary uniform across every session. The draft's own preview button ("Nochmal abspielen") belongs to the *canvas*, not the app; the shipped screen has no visible control, so the whole screen is tap-to-continue (like the study card) plus a fixed timeout, so nobody who doesn't realize they can tap gets stuck. The draft's flame is orange on its own dark background — deliberately not carried over; the app's colour rule (`success`/`warning` reserved for immediate feedback, never a second accent) applies here exactly as it does to the inline streak row in `SessionDone`, so the flame stays `T.primary` in both places.
- **The card view opens on the *decks*, not on the cards** (`browseStapel` in `App.jsx`; `null` means the overview). Throwing a grown collection at the reader as one flat list is what made the view unusable to look at, quite apart from how fast it rendered. `filtered` starts from `cards.filter(c => deckKeyOf(c) === browseStapel)`, so search, sort, selection and bulk delete all act inside the open deck only — "Alle" never selects the whole collection. Leaving the view resets to the overview. **The Fehlerkartei is deliberately absent here**: it is a cross-section (`isDifficult()`), not a deck, and its cards already sit in their language deck — listing it would show them twice. It stays on the dashboard, where it is a place to *study*, not to manage.
- **The card list renders only what is on screen** (`src/hooks/useFensterListe.js`). Measured with 800 cards before it existed: 504 ms to build the view, 9 702 DOM nodes, ~90 ms per keystroke in the search box. After: ~190 ms, ~450 nodes, and flat at 2 000 cards. Three things hold it together and any rewrite must keep all three: rows have a **fixed height** (`ZEILE_H` in `App.jsx`) because the spacers above and below are computed from it — variable heights make the list jump, which is why rows clip their text instead of wrapping; the hook keeps its container **in state, not a ref**, since the list is mounted only when the card view opens and a ref changing would not re-run the effect (the first attempt did exactly that and rendered an empty list); and `search` stays the immediate input value while a debounced `sucheAktiv` feeds the filter, so typing never waits on a re-filter.
- **The card list's layout rules live in `globalCss`, never inline** — same trap as the navigations below, but with `flex` and `bottom` instead of `display`. An inline `flex: 1` on the search box beat the media query and squeezed both dropdowns to 55 px; `inputStyle` carries `width: '100%'`, so the selects pass `width: undefined` to let the CSS decide. The selection bar's `bottom` is a CSS rule for the same reason: on phones it has to clear the floating nav pill.
- **Nav visibility is driven purely by CSS media queries** (`.nav-top-links` / `.nav-bottom` in the `globalCss` template string). Top nav on wide screens, floating bottom pill on phones. Putting an inline `display` on either element silently defeats the breakpoint and shows **both** navigations at once — this has already happened once.
- **Speech voices load asynchronously.** `getVoices()` is usually empty on first call, so `App.jsx` caches them in a ref and refreshes on `voiceschanged`. Some browsers also ignore `utterance.lang` unless an explicit `voice` is set, which is why the code resolves a matching voice (exact region first, then language prefix).
- PWA is configured for `autoUpdate` + `skipWaiting` in `vite.config.js`, so users get new versions on next launch without reinstalling. Supabase responses are deliberately **not** runtime-cached — a failed request should retry later, not serve stale data.

### `.claude/skills/spanischcoach/`

A skill that lets Claude act as a chat-based Spanish coach, sharing the app's data model and FSRS formulas so cards are interchangeable between the app and chat sessions.

- `scripts/vocab.js` — dependency-free Node ESM CLI (`add-vocab`, `add-gap`, `due`, `rate`, `stats`, `list`) reading/writing `data/spanischcoach/vocab.json` in the same shape as the app's JSON export. Ratings should always go through this script rather than being computed by hand, so results stay bit-for-bit consistent with `rate()`.
- **`rate()`, the FSRS formulas, the card shape, and `splitAnswer()`/`cardSides()` are duplicated (not imported) here** so the script runs without a build step — **changes to any of those must be mirrored into `vocab.js`.** `splitAnswer()` is critical because it defines what counts as a correct answer: if the two sides disagree on the answer/example separator, something the app accepts would be marked wrong in chat, and vice versa. `cardSides()` matters for the same reason on the *question* side — without it the script prints the example sentence inside the prompt. When adding separator patterns to `splitAnswer()` in `srs.js`, always update the regex in both files identically. UI-only concerns (theme, view logic, the language picker lists) are not. The target retention is mirrored as a constant (`RETENTION = 0.95` in both); the script deliberately ignores the `retention` field of the JSON, so an older export carrying a density-knob value cannot make chat schedule differently from the app. `EARLY_STEPS`, `HARD_FAKTOR`/`hardInterval()` and the `earlyStep`/`recoveryStreak` bookkeeping are mirrored for the same reason (the script reads neither, but a card rated in chat would otherwise return to the app with a stale streak and fall out of the Fehlerkartei at the wrong moment) — a divergence there moves a card's due date by weeks, and it is verifiable: rating the same fresh card "Gut" eight times must yield `1 → 3 → 7 → 16 → 35 → 70 → 140 → 272` in both.
- The app's "Karten → Export/Import" is the bridge between `localStorage` (browser) and `data/spanischcoach/vocab.json` (repo/chat), and remains the only way to move cards without signing in.

## Language

The app, all UI copy, and the code comments are in German. Commit messages and comments in this repo are written in German prose that explains *why* a non-obvious decision was made, not what the line does — match that register.
